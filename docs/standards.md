# 개발 기준

## 변경 경계

- 페이지와 HTTP 진입점은 요청·응답과 화면 조합을 맡고, 재사용되는 데이터 접근과 제품 로직을 직접 누적하지 않는다. 같은 데이터 규칙이 두 진입점에서 필요하면 기능 계층으로 옮긴다.
- 기능 계층은 화면 구성 요소를 가져오지 않는다. 공통 기반 코드는 특정 페이지나 화면 구성 요소에 의존하지 않는다. 이 방향을 거스르는 import가 생기면 구조 위반이다.
- 서버에서 이미 실행 중인 페이지는 자기 HTTP 주소를 호출하지 않고 데이터 계층을 직접 사용한다. 내부 HTTP 왕복이 추가되면 위반이다.
- 사용자 입력은 서버 경계에서 스키마로 검증하고, 사용자 소유 데이터 조회·변경은 명시적인 사용자 ID 또는 데이터베이스 권한 정책을 통과해야 한다.

## 데이터베이스와 외부 서비스

- 스키마, 함수, 인덱스와 권한 변경은 새로운 순번의 마이그레이션으로 추가한다. 이미 적용된 마이그레이션을 수정해 이력을 다시 쓰면 안 된다.
- 데이터 보존이 필요한 환경에 `supabase db reset`을 실행하지 않는다. 초기화가 필요한 경우 삭제 대상과 계정 재생성 절차를 사용자에게 먼저 확인한다.
- 모든 사용자 소유 테이블은 사용자 ID 격리를 유지하고, 새 테이블과 함수는 익명 역할의 권한과 행 단위 정책을 명시적으로 검토한다.
- 브라우저 코드와 공개 환경값에 높은 권한 키를 포함하지 않는다. 서버 전용 값이 클라이언트 번들에 나타나면 배포 차단 사유다.
- 외부 패키지는 표준 API와 현재 의존성만으로 요구사항을 충족할 수 없고, 추가 패키지가 실제 실행 경로에서 사용되는 경우에만 추가한다. 추가 시 사용 위치, 대체하지 못한 기존 수단, 번들·운영 영향을 변경 설명에 남기고 `package-lock.json`을 함께 갱신한다.

## Next.js와 TypeScript

- 설치된 Next.js 버전의 API를 기준으로 작업한다. Next.js 코드 변경 전 `node_modules/next/dist/docs/`의 관련 문서를 읽고 폐기 예정 API를 새로 도입하지 않는다.
- TypeScript 엄격 검사를 유지한다. 새 `any`, 파일 단위 검사 제외, 설명 없는 `@ts-ignore`, 입력 검증 전에 외부 값을 도메인 타입으로 단언하는 방식으로 오류를 숨기면 검사 실패로 취급한다.
- 서버 구성 요소와 클라이언트 구성 요소의 경계를 명시적으로 유지한다. 상태·이벤트·브라우저 API가 필요하지 않은 페이지 데이터 조회를 클라이언트로 옮기지 않는다.

## 변경 완료 조건

- 기능 또는 버그 수정은 관련 단위 테스트와 함께 `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`를 통과해야 한다. 검사 자체가 실행되지 않았거나 assertion 전에 종료된 경우 성공으로 간주하지 않는다.
- lint 경고는 오류가 아니라는 이유로 숨기지 않고 변경과 관련 있는지 검토한다. 새 경고를 추가하면 완료로 간주하지 않는다.
- 인증, 권한, 데이터 마이그레이션, 파일 업로드, 가져오기, 브라우저 상호작용은 자동 검사만으로 끝내지 않고 해당 SQL 또는 실제 브라우저 흐름을 확인한다.
- 기능 또는 버그 수정이 끝나면 변경 내용을 검토한 뒤 커밋하고 `origin/main`에 푸시한다. 사용자가 아직 결과를 승인하지 않았거나 unrelated 변경이 섞여 있으면 먼저 분리·확인한다.
- 비밀과 `.env.local`, 사용자 데이터, 생성된 로컬 작업 상태를 커밋하지 않는다.

## 제품 일관성

- 사용자와의 작업 대화 및 사용자에게 보이는 기본 문구는 한국어를 사용한다.
- 새 문서 주소는 한글을 포함할 수 있어야 하며, 동적 문서 경로는 안전한 디코딩을 거친 뒤 조회한다.
- 문서 저장 경로를 추가할 때 리비전 생성과 링크 재색인의 원자성을 깨지 않는다.
- 테마의 색상 값은 테마별로 관리하되 카드 모서리, 공통 간격, 제목 굵기 같은 형태 값은 모든 테마에 동일하게 적용한다. 테마 대표색을 바꾸면 설정 화면의 스와치 값도 함께 바꾸고 실제 전환을 확인한다.
