# GitHub Actions 중심 CI/CD 배포 전략 (제안, 미채택)

> 2026-09-16 작성. 아직 결정된 사항이 아니다. 실행 파일(`.github/workflows/*.yml`)은 만들지 않았고,
> 아래 방향에 동의한 뒤 별도 작업으로 구현한다. 전체 시각 자료는
> [claude.ai 아티팩트](https://claude.ai/artifact/6pYhfGfZ4fRNjDfEgGY8Ps)에도 있다(외부 링크, 만료·접근 변경 가능성 있음 — 이 파일이 원본 기록).

## 요약

1. PR마다 lint·타입체크·유닛테스트·빌드·**SQL 마이그레이션 안전 검사**를 자동 실행한다.
2. `main` 병합 시에만 배포하며, 프로덕션 배포 직전에 **수동 승인 게이트**를 둔다.
3. "기존 마이그레이션 수정 금지" 규칙([standards.md](../standards.md))을 CI가 자동으로 강제하도록 만든다.
4. 앱 롤백은 배포처 기능으로 즉시 가능하지만, **DB 백업·복구 리허설은 아직 없다** — 가장 먼저 메워야 할 구멍.
5. 도입은 4단계로 나누고, 배포처를 정하기 전인 지금도 1·2단계는 먼저 시작할 수 있다.

## 1. 브랜치·환경 모델

단일 소유자 프로젝트라 복잡한 브랜치 전략은 불필요하다. `main` 하나를 배포 기준으로 두고,
기능 작업은 짧게 산 브랜치 → PR → 머지로 흐른다.

- **Preview (PR별)**: PR을 열면 자동 생성. 코드 검토와 실제 화면 확인용. 프로덕션 DB에 절대 연결하지 않는다.
- **Production**: `main` 병합 후에만, 수동 승인을 거쳐 배포. 실제 사용자 데이터가 있는 유일한 환경.

**결정 필요**: Preview가 쓸 DB를 어떻게 마련할지 — (a) Supabase 프리뷰 브랜치 기능으로 PR마다 임시 DB를 뜨거나,
(b) 스키마만 있고 데이터는 거의 없는 공유 스테이징 프로젝트 하나를 계속 재사용. (a)가 더 안전하지만 유료 플랜이 필요할 수 있다.

## 2. CI — PR을 열 때마다

병합 전에 실패해야 할 것은 전부 여기서 걸러낸다. 하나라도 실패하면 머지가 막힌다.

| 단계 | 명령 | 실패 조건 |
|---|---|---|
| 설치 | `npm ci` | 의존성 설치 실패 |
| Lint | `npm run lint` | 오류 0건이 기준. 기존 이미지 경고 2건은 변경과 무관하면 통과 |
| 타입 검사 | `npm run typecheck` | 경로 타입 재생성 포함, 하나라도 타입 오류 시 실패 |
| 유닛 테스트 | `npm test` | 현재 164개 — 새 실패 또는 커버리지 없는 위험 변경 시 리뷰에서 반려 |
| 빌드 | `npm run build` | 타입은 통과해도 빌드 시점에만 드러나는 오류(서버/클라 경계 등)를 잡음 |
| 마이그레이션 게이트 | 아래 3절 | - |

## 3. 마이그레이션 안전 게이트

`docs/standards.md`가 이미 정한 규칙 — "스키마 변경은 새 마이그레이션으로만 추가하고, 기존 마이그레이션을
고쳐 이력을 다시 쓰지 않는다" — 를 CI가 기계적으로 확인한다. 사람이 리뷰에서 놓치는 순간이 가장
위험하므로 자동화 우선순위가 가장 높다.

| 검사 | 방법 | 막는 사고 |
|---|---|---|
| 기존 파일 수정 금지 | `git diff --name-status origin/main...HEAD -- supabase/migrations/` 결과에 `M`/`D`가 있으면 실패 | 이미 배포된 마이그레이션을 고쳐서 이력이 꼬이는 것 |
| 순방향 적용 확인 | Postgres 서비스 컨테이너에 전체 마이그레이션을 처음부터 순서대로 적용 | 로컬에서만 통과하고 깨끗한 DB에는 실패하는 마이그레이션 |
| SQL 테스트 | 저장소에 이미 있는 `*.sql` 테스트 파일 실행 (RLS·권한 포함) | 권한 정책이 의도와 다르게 열리거나 막히는 것 |

## 4. CD — main 병합 시

1. 02절 전체 재실행 (재검증)
2. GitHub Environment 수동 승인 대기
3. 프로덕션 DB에 마이그레이션 먼저 적용
4. 앱 배포 (코드는 그다음)
5. 스모크 확인 (로그인 → 문서 목록 200 OK)

순서가 중요하다: **DB 마이그레이션이 앱 코드보다 먼저** 적용돼야, 새 코드가 아직 없는 컬럼·함수를
찾다가 터지는 상황을 피한다. 반대로 컬럼을 없애는 마이그레이션은 그 컬럼을 더 이상 안 쓰는 코드가
먼저 배포된 뒤에 와야 한다 — 두 규칙 모두 "무엇을 어떤 순서로 배포 가능한가"를 PR 리뷰에서 사람이
판단해야 하는 지점이다.

## 5. 승인 게이트와 롤백

| 상황 | 대응 | 현재 상태 |
|---|---|---|
| 앱 코드가 잘못 배포됨 | 배포처의 이전 배포로 즉시 롤백 | 거의 무료로 가능 (배포처 기능) |
| 마이그레이션이 잘못됨 | 기존 마이그레이션을 되돌리지 않고, 문제를 고치는 새 마이그레이션을 추가 | 규칙상 이미 안전한 방향 |
| 데이터가 실제로 손상됨 | 백업에서 복구 | **백업·복구 리허설 없음** |

**현재 구멍**: [findings.md](findings.md)에 이미 적혀 있듯, 정기 백업과 복구 리허설 자체가 없다.
프로덕션에 실제 사용자 데이터가 쌓이기 전에 가장 먼저 메워야 할 부분 — CI/CD보다 우선순위가 높을 수 있다.

## 6. 시크릿 관리

GitHub Actions의 Environment별 Secrets를 쓴다 — Preview용과 Production용을 분리해서, PR 단계
워크플로가 실수로라도 프로덕션 자격 증명에 닿지 않게 한다.

| 시크릿 | 범위 | 주의 |
|---|---|---|
| Supabase 접근 토큰·DB 연결 문자열 | Preview / Production 분리 | PR 워크플로는 절대 프로덕션 값을 보지 않음 |
| 배포처 배포 토큰 | Production 전용, 승인 게이트 뒤에서만 사용 | - |
| OpenAI/Anthropic 키 | 사용자 BYOK — 앱 DB에 암호화 저장, CI/CD와 무관 | 이미 설계대로 분리되어 있음 |

**결정 필요**: 저장소를 공개로 둘 계획이 있다면, 포크에서 열린 PR은 시크릿에 접근하지 못하도록
워크플로 트리거를 `pull_request`로 한정해야 한다(`pull_request_target` 오남용 금지).

## 7. 운영 관찰성

`docs/security.md`가 이미 "로그에 문서 본문·주석 내용·검색어 전체·인증 토큰을 남기지 않는다"고
정해뒀다. 모니터링 도구를 더하더라도 이 제약이 우선한다.

- **헬스체크 엔드포인트** — 배포 직후 스모크 확인과 가동 모니터링 양쪽에 필요, 현재 없음
- **에러 모니터링 (선택)** — Sentry 등, 본문·검색어를 이벤트에 담지 않도록 스크러빙 설정 필수
- **배포 알림** — 배포 성공/실패를 어디로 알릴지 (이메일이면 충분한 규모)

## 8. 제안하는 도입 순서

배포처를 아직 정하지 않았어도 1·2단계는 지금 바로 시작할 수 있다.

1. **기본 CI만 먼저** — lint·typecheck·test·build를 PR마다. 배포처 결정과 무관하게 오늘 시작 가능.
2. **마이그레이션 게이트 추가** — 3절의 세 가지 검사. 배포처와 무관하게 지금 넣을 수 있고, 가장 사고를 많이 막아준다.
3. **Preview 배포 연결** — 배포처가 정해진 뒤. PR마다 실제로 눌러볼 수 있는 화면이 뜨도록.
4. **승인 게이트를 포함한 프로덕션 CD** — 백업·복구 리허설을 먼저 한 번 실제로 해본 뒤에 진행. 순서를 바꾸지 않는 것을 권장.

## 9. 정리 — 결정할 것 전부

- **배포처** — Vercel / Netlify / VPS·Fly.io (별도로 논의한 선택지)
- **Preview DB 방식** — Supabase 프리뷰 브랜치 vs 공유 스테이징 프로젝트
- **승인 게이트 구성** — 본인 혼자 승인해도 되는지, 승인 전 대기 시간을 둘지
- **백업 주기·보관 기간** — 배포처 결정과 맞물림, Supabase Cloud 유료 플랜의 자동 백업 활용 여부
- **저장소 공개 여부** — 포크 PR 시크릿 격리 정책에 영향
- **E2E 테스트 도입 시점** — 현재는 유닛테스트 + 수동 브라우저 검증만 존재. CD 이전에 추가할지는 선택
