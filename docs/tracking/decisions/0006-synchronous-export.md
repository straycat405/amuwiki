# 동기 방식 전체 내보내기

## 배경

제품 설계 14절은 내보내기를 `export_jobs`(큐·상태·서명 URL·만료) 기반 비동기 작업으로 정의한다. 하지만 배포·운영 방식이 아직 정해지지 않아([findings.md](../findings.md) 참조) 이 작업을 실행할 워커나 스케줄러를 어디에 둘지 정할 수 없고, 현재 단일 소유자 사용량(문서 20여 개, 첨부 수 MB 수준)에서는 요청-응답 안에서 ZIP을 만드는 데 몇 초도 걸리지 않는다.

## 결정

`/api/export`가 요청 안에서 Markdown·manifest.json·index.md·첨부파일을 모아 ZIP을 만들어 바로 응답으로 스트리밍한다. `export_jobs` 테이블, 큐 상태, 서명 URL, 만료 정리 작업은 만들지 않는다. 설정 화면에는 상태 표시 없이 문서·첨부 수 요약과 다운로드 버튼만 둔다.

이는 [0005-explicit-server-save](0005-explicit-server-save.md) 이후 임시 문서 정리 기능에서 이미 채택한 "배포 방식이 정해지지 않은 동안은 수동 버튼으로 충분히 해결하고, 자동 스케줄링은 인프라가 정해진 뒤 추가한다"는 방향과 같다.

## 검토한 대안

- 설계 그대로 `export_jobs` 비동기 작업과 서명 URL을 구현하는 방식은 지금 규모에 맞지 않게 크고, 배포 대상이 정해지지 않아 만료 정리를 실행할 곳이 없어 선택하지 않았다.
- Storage에 결과물을 올리고 서명 URL만 발급하는 절충안도 검토했지만, 굳이 원본을 서버에 남겨 정리 대상을 하나 더 만들 이유가 없어 요청 응답으로 바로 스트리밍하는 쪽을 택했다.

## 결과

문서·첨부가 지금보다 훨씬 많아지거나 요청 시간 제한이 있는 호스팅으로 배포하기로 정해지면, 이 결정을 다시 검토하고 설계 14절의 비동기 작업 방식을 도입해야 한다. 그 전까지 `/api/export`는 매 요청마다 전체 문서를 다시 읽고 ZIP을 새로 만든다.
