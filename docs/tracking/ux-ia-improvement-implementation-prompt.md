# UX·정보구조 개선 작업 지시 프롬프트

아래 리포트를 근거로 아무위키의 첫 사용 경험과 핵심 연결 탐색 경험을 개선해 주세요.

- 기준 리포트: `docs/tracking/ux-ia-diagnostic-report-2026-09-16.md`
- 제품 규칙: `docs/business-rules.md`
- 변경 전 반드시 읽을 문서: 루트 `AGENTS.md`, `docs/standards.md`, `docs/engineering-notes.md`, 변경 영역의 `AGENTS.md`

## 목표

처음 방문한 사용자가 첫 2분 안에 다음을 이해하고 실행할 수 있게 만드세요.

1. 새 문서를 쓰거나 기존 Markdown을 가져올 수 있다.
2. 문서를 `[[개념]]`으로 연결할 수 있다.
3. 연결 문서를 현재 문맥 안에서 카드로 탐색할 수 있다.
4. 현재 편집 내용이 서버 저장인지 브라우저 임시 저장인지 알 수 있다.

이번 작업은 색상·여백·아이콘 위주의 미세 조정이 아닙니다. 제품 구조, 행동 규칙의 발견성, 피드백의 의미를 개선하세요. 기존 문서·첨부파일·리비전·사용자별 권한 격리를 깨면 안 됩니다.

## 구현 범위

### 1. 빈 홈의 시작 경로

- 문서가 없을 때 `새 문서 작성`과 `Markdown 가져오기`를 동등한 주요 행동으로 보여 주세요.
- 가져오기는 기존 `/settings/import` 흐름을 재사용하세요. 가져오기 로직, 권한, 데이터 수명주기는 바꾸지 마세요.
- 제품 설명은 한두 문장으로 제한하세요. Wiki link와 카드 탐색이라는 차별 행동을 이해할 수 있어야 합니다.
- 가능한 경우 예시 문서 또는 저장 없이 볼 수 있는 짧은 안내를 제공하세요. 사용자의 실제 문서를 자동 생성해서는 안 됩니다.

### 2. 신규 문서 작성의 저장·연결 안내

- 편집기에 `이 브라우저에 임시 저장됨`, `서버에 저장됨`, `저장 중`처럼 현재 상태를 구분해 보이세요.
- 기존 로컬 임시 저장과 명시적 서버 저장의 동작은 유지하세요. 서버 저장 성공 전에 로컬 초안을 지우면 안 됩니다.
- 복원된 신규 문서 초안은 사용자가 출처를 알 수 있게 표시하세요. 사용자가 선택하기 전 내용을 지우지 마세요.
- 빈 본문에는 Markdown 문법 나열이 아니라 `[[관련 문서]]`로 연결을 만드는 행동 중심 안내를 제공하세요.

### 3. 검색 피드백 수정

- 전역 검색에서 요청이 진행 중일 때 `검색 결과가 없습니다`를 보여 주지 마세요.
- 150ms 디바운스 뒤 서버 응답을 기다리는 동안 `검색 중…` 또는 동등한 진행 상태를 보여 주세요.
- 응답이 확정된 뒤에만 빈 결과를 보여 주세요.
- 기존 키보드 탐색, 최근 검색어, 최근 문서, 검색 결과 우선순위를 보존하세요.

### 4. Wiki link 카드 탐색을 제품 규칙에 맞추기

- 고정 카드는 최대 3개만 동시에 보이도록 바꾸세요. 이 값은 `docs/business-rules.md`의 규칙을 따릅니다.
- 네 번째 탐색부터는 이전 탐색을 잃지 않도록 경로로 접거나, 교체 결과를 사용자에게 명확히 보여 주세요. 단순히 실패시키거나 아무 설명 없이 카드를 닫지 마세요.
- 첫 카드 탐색에서만 “클릭하면 현재 문서를 떠나지 않고 관련 문서를 엽니다”라는 짧은 안내를 제공하세요.
- 카드 안의 현재 문서 이동, 새 탭 열기, 닫기 행동을 접근성 이름과 사용자 문구에서 명확히 구분하세요.
- 일반 링크 이동을 막는 현재의 키보드·수정키 동작과 Escape 닫기, 화면 경계 처리, 중첩 미리보기 금지 규칙을 보존하세요.

### 5. 전역 탐색 신뢰 수정

- 푸터의 `문서`, `휴지통`, `설정` 링크가 각각 실제 목적지로 이동하게 고치세요.
- 가져오기·내보내기·휴지통·정리 기능의 전체 정보구조 재편은 이번 범위에서 설계 제안만 남기고, 사용자가 별도로 승인하기 전에는 대규모 경로 변경을 하지 마세요.

## 완료 조건

1. 관련 단위 테스트를 추가·수정하고 `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`를 실행하세요.
2. 로그인된 실제 브라우저에서 다음을 검증하세요: 빈 홈의 두 시작 경로, 신규 문서의 임시 저장·명시적 저장 상태, 검색 중 상태와 결과, 카드 3개 제한과 네 번째 행동, 푸터 목적지.
3. 새 문서·첨부·기존 사용자 데이터를 검증 목적으로 만들었다면, 삭제 전 대상을 확인하고 사용자 승인 없이는 파괴적 정리를 하지 마세요.
4. 변경한 파일, 검증 결과, 남은 설계 결정(특히 네 번째 카드의 경로 표현 방식)을 한국어로 짧게 보고하세요.

## 구현 판단 기준

- 익숙한 사용자에게 기능을 더 보태는 것보다, 처음 사용자가 다음 행동을 추측할 수 있게 만드는 쪽을 선택하세요.
- 새 패키지는 표준 API와 현재 의존성으로 해결할 수 없을 때만 추가하세요.
- 기존 인증, 사용자별 데이터 격리, Markdown 내보내기 호환성, 명시적 저장의 원자성을 변경하지 마세요.
